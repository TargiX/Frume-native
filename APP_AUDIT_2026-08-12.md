## 1. Decision and recommended product focus

The correct near-term move is to freeze new cut-style work and make the existing loop safe, compliant, and repeatable:

1. Withdraw build 2 from consideration and repair the release inputs.
2. Decide and implement a compliant photo-delivery contract.
3. Make session replacement and Unsplash-use tracking transactional.
4. Fix the reproduced recovery, timer, and replay-state defects.
5. Add first-run teaching and a durable reason to return.
6. Validate the exact signed candidate on physical devices and TestFlight.

The current product proposition is clear — a calm, tactile photo puzzle — but most paid cuts change shape rather than interaction. Because the engine snaps pieces to absolute target slots and does not support clusters or rotation, the difference between free and paid play is mainly visual. That is a product-depth risk, not a correctness bug. Do not block a narrow 1.0 on clusters and rotation, but treat at least one deeper interaction or retention mechanic as the next product milestone.

### Core-loop conclusion

The minimum loop works once, but the **repeat loop is thin**. The highest-value additions are not more cuts. They are:

- reliable resume/replacement behavior;
- first-run gesture teaching;
- same-theme and same-photo continuation;
- durable completion history or personal bests;
- visible progress without opening accessibility output;
- one retention mechanic such as a daily puzzle, streak, or small completed-photo shelf.

Clusters and rotation would add genuine mechanical depth, but should be scoped as a separate engine milestone after 1.0 stability. A simpler 1.0 may intentionally ship the current slot-matching mechanic, provided the store copy does not imply a traditional interlocking/rotating jigsaw experience that is not present.

## 5. P1 — release blockers

### REL-01 — Build 2 was uploaded from a source archive with a RevenueCat test key

**Evidence:** Artifact-confirmed and reproduced across equivalent configuration. The bundled `main.jsbundle` in the local `1.0.0 (2)` source archive used for the successful Organizer upload contains a `test_` RevenueCat key. A source-equivalent configured Release simulator build showed RevenueCat’s wrong-key alert and terminated after acknowledgement. The archive app is development-signed (`get-task-allow=true`), and Apple can re-sign/transform the upload; this audit therefore does not claim byte-for-byte identity with the processed App Store binary.

**Impact:** Build 2’s release inputs are invalid and produce an unusable launch. Build 2 must not advance to review; if it is already distributed, treat it as an availability incident.

**Fix:**

1. Configure the iOS public production key with the expected `appl_` prefix in the release environment.
2. Invalidate build 2 as a candidate; increment to build 3 or later.
3. Extend the archive guard to reject absent keys, `test_` keys, Android keys, and unexpected prefixes.
4. Scan the exact exported/archive bundle, not only source environment files.

**Acceptance criteria:**

- The source archive/bundle used for the build 3+ upload contains one expected `appl_` public key and no `test_` key.
- Cold launch reaches Home on a clean physical install.
- Sandbox purchase, cancellation, interrupted purchase, and restore pass in TestFlight.
- Entitlement persists after force-quit and in documented offline-cache scenarios.
- After reinstall, an online Restore Purchases action recovers the entitlement; subsequent supported offline relaunches retain it according to the documented cache contract.

### REL-02 — Public support and privacy URLs redirect to authentication

**Evidence:** Live-verified. Anonymous requests to `https://frume-support.vercel.app/` and `/privacy/` returned a redirect to Vercel SSO rather than public content.

**Impact:** Reviewers and users cannot reach required support/privacy content. Apple explicitly calls out functional links and current support information in its [App Review guidance](https://developer.apple.com/app-store/review/) and [Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).

**Fix:** Disable deployment protection for the production support site or move the pages to a truly public deployment. Keep preview deployments protected if desired.

**Acceptance criteria:**

- Anonymous `GET` and browser navigation, with no existing cookies, return HTTP 200 and readable content.
- Privacy URL points directly to the privacy page, not a shell or login redirect.
- Links work from the built app and App Store metadata on cellular and Wi-Fi.
- A release guard checks final redirect destination, status, content type, and a known page marker.

### CMP-01 — Current Unsplash persistence path conflicts with standard hotlinking guidance

**Evidence:** Code-confirmed. `ExpoPuzzleImageFileStore` downloads provider images into app storage; `PuzzleImageCache` replaces the display URI with the local file; `PuzzleBoard` renders the remote URI only if local rendering fails (`src/puzzle/persistence/ExpoPuzzleImageFileStore.ts:42`, `src/puzzle/persistence/PuzzleImageCache.ts:99`, `src/puzzle/render/PuzzleBoard.tsx:391`).

Unsplash’s standard API guidance says applications should use the image URLs returned by the API for display. See [Hotlinking Images](https://help.unsplash.com/en/articles/2511271-guideline-hotlinking-images) and the [API Guidelines collection](https://help.unsplash.com/en/collections/1451694-api-guidelines).

**Impact:** A core offline/resume behavior may violate the provider contract even if download tracking is sent correctly. This is a compliance and continuity blocker until the contract is explicit.

**Fix options:**

- **Preferred:** hotlink provider photos and redesign offline/resume behavior around the remote URL and permitted caching semantics.
- Obtain a written Unsplash exception for the exact local-persistence and future-display behavior.
- Move curated photos to owned/licensed infrastructure with a contract that permits persistent local copies.
- Narrow 1.0 to user-owned photos while the remote-photo contract is resolved.

**Acceptance criteria:** Written policy/contract decision, implementation matching it, and a test covering initial display, resume, offline behavior, and deletion/expiry.

### CMP-02 — Provider attribution is intentionally limited to setup and puzzle options

**Evidence:** Code-confirmed. Setup renders photographer credit, but Home displays a provider photo without visible credit; active-game credit is available only inside the menu; completion hides the HUD/menu and shows no credit (`DifficultyScreen.tsx:510`, `PlayHomeScreen.tsx:187`, `PuzzleMenuSheet.tsx:603`, `GameScreen.tsx:447`, `PuzzleCelebration.tsx:131`).

Unsplash's API terms require attribution to the photographer and Unsplash each time an API image is displayed. See [API Terms, section 9](https://unsplash.com/api-terms) and the [Attribution Guideline](https://help.unsplash.com/en/articles/2511315-guideline-attribution).

**Impact:** Setup/options-only attribution preserves the intended quiet gameplay presentation, but it does not match the literal standard API attribution contract. This remains a release compliance decision rather than a locally closed UI defect.

**Product decision:** Keep linked credit on setup and in puzzle options. Do not add persistent credit chrome to Home, the gameplay HUD, or completion without explicit product approval. Preserve the attribution metadata so those existing links survive resume.

**Acceptance criteria:** Obtain written permission from Unsplash for this exact placement, or move curated photos to a provider/license that permits it. Record the decision before release; own photos must never display provider attribution.

### OPS-01 — Worker controls do not enforce a safe global provider budget

**Evidence:** Code-confirmed. Requests without `Origin` are allowed; `/photo` is limited to 60/minute/IP; each returned photo creates a single-use grant with a 7-day TTL plus grace; `/track` is limited by the caller-controlled grant token rather than the originating IP/device; consuming a grant triggers the provider request (`server/src/index.ts:323`, `:798`, `:842`, `:979`, `:1048`, `:1080`, `:1134`; `server/wrangler.jsonc:24`).

The configured 60/minute rule gives a **theoretical per-IP issuance ceiling** of 3,600 grants/hour; Cloudflare window behavior means this is not a promise of exact throughput. It is nevertheless above Unsplash’s documented default production allowance of 1,000 JSON requests/hour, and distributed callers scale further. See the official [Unsplash API rate-limit documentation](https://unsplash.com/documentation). CORS does not protect a public HTTP endpoint from scripts or native clients.

**Impact:** Upstream quota exhaustion, unexpected cost, degraded photo loading for all users, and operational abuse.

**Fix:**

- Add a hard global hourly provider budget with reserve capacity and a kill switch.
- Bind grant consumption to server-recorded issuance context; add IP/device budgets and anomaly detection.
- Consider App Attest or equivalent application-instance proof, understanding it is an abuse-reduction layer rather than sole authorization.
- Bound outstanding grants per source and shorten TTL to the minimum product need.
- Emit metrics for issued, consumed, expired, rejected, upstream-success, and upstream-failure events.

**Acceptance criteria:** Load/abuse tests cannot exceed the configured global budget; alerts fire before exhaustion; legitimate clients degrade gracefully; key rotation and emergency disablement are documented.

### TXN-01 — Photo-use tracking is not atomic with making a session resumable

**Evidence:** Code-confirmed. Setup waits for `startSession`, which installs and persists the new session, and enqueues the photo-use event afterward (`DifficultyScreen.tsx:365`; `usePuzzleSession.ts:246`, `:595`). Next-puzzle replacement similarly installs/schedules before the durable enqueue (`usePuzzleSession.ts:329`, `:709`; `nextPuzzle.ts:109`). A force-quit in that window leaves a resumable provider-photo session without its expected use event.

**Impact:** Provider-compliance events can be lost while the user-visible state survives. The same ordering makes recovery reasoning difficult.

**Fix:** Introduce a candidate transaction:

1. Resolve and validate photo + cut into a candidate that is not yet active.
2. Durably enqueue the required provider event.
3. Atomically commit the session pointer and image ownership metadata.
4. Only then navigate/render it as the active session.
5. On failure, preserve the previous session and release candidate files.

**Acceptance criteria:** Integration tests force-quit or throw after every transaction step, remount storage, and prove exactly one of two states: old session intact, or new session resumable with its durable event queued.

### DATA-01 — Starting a new photograph silently and destructively replaces progress

**Evidence:** Code-confirmed. Persistence uses one active key, Home offers “New photograph” with no confirmation, and session start replaces the current session. A tested four-slot `sessionShelf` implementation exists but is not imported into the product path (`PlayHomeScreen.tsx:263`; `usePuzzleSession.ts`; `src/puzzle/persistence/sessionShelf.ts`).

**Impact:** Users can lose an unfinished puzzle when they successfully start the newly configured puzzle, including one backed by their own photo. The initial **New photograph** tap only opens Gallery; the destructive replacement occurs later without confirmation when Start commits. This still contradicts the confidence implied by resume/save messaging.

**Fix:** For the smallest 1.0 change, present an explicit replacement confirmation and keep the previous session until the new candidate commits. For the better product outcome, connect the existing shelf end-to-end, including image reference ownership, eviction, entitlement changes, and UI.

**Acceptance criteria:** Cancel preserves progress; any start failure restores the exact previous session; replacement cannot orphan/delete its image; shelf eviction is deterministic and tested if enabled.

### NAV-01 — Back navigation does not cancel puzzle preparation

**Evidence:** Code-confirmed. The setup `onPlay` path awaits photo/cache/cut/session work without an unmount/focus generation guard. The stack header Back remains active, and image acquisition can wait up to 20 seconds (`DifficultyScreen.tsx:352`; `PlayStackNavigator.tsx:19`; `ExpoPuzzleImageFileStore.ts:52`).

**Impact:** Start → Back can later persist/track a session or navigate to Game after the user has left, potentially replacing prior progress invisibly.

**Fix:** Give each preparation run an operation ID and `AbortController`; invalidate it on blur/unmount/back; check it before every durable write, event enqueue, state install, and navigation. Disable duplicate Start requests while one is active.

**Acceptance criteria:** Lifecycle test covers Back, rapid double Start, background, and unmount at each await boundary; none may navigate or mutate after cancellation.

### FLOW-01 — “Try again” after an invalid own photo starts remote search

**Evidence:** Reproduced. A deliberately over-wide own photo correctly triggered validation. Tapping **Try again** did not reopen the system picker; it invoked curated photo loading and then displayed “Failed to load photo” in a no-config build. The retry callback shares the generic photo-fetch path (`GalleryScreen.tsx:143`, `:181`, `:304`).

**Impact:** The user cannot recover naturally from a validation error in a core acquisition path and may unexpectedly invoke network content.

**Fix:** Model retry by source. Own-photo validation errors reopen the system picker; remote-search errors retry the same category/request; permission errors open the correct settings guidance.

**Acceptance criteria:** Automated navigation test asserts each error type exposes only its correct recovery action and never crosses data sources.

### FILE-01 — Photo storage, backup, and deletion behavior contradict the documented lifecycle

**Evidence:** Code-confirmed storage and deletion paths; backup participation remains a device-level risk to verify. Both remote provider files and imported own photos are copied beneath app Documents, and the code does not set a backup-exclusion attribute (`ExpoPuzzleImageFileStore.ts:47`, `:78`; `ownPhotoLibrary.ts:41`). Apple recommends Caches for purgeable data and explicit exclusion for nonpurgeable data that is inappropriate for backup; see [Optimizing Your App’s Data for iCloud Backup](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup). An actual created file’s resource values were not inspected in this audit.

`pruneOwnPhotos` is called only after another own-photo import (`pickOwnPhoto.ts:62`). Completion, `clearSession`, and replacement by a provider photo do not prune `frume-own-photos`. During another own-photo import, pruning deliberately keeps both the prior saved image and the newly imported image, but there is no post-commit cleanup of the prior image. This disagrees with the public privacy page’s promise that a photo is deleted when no longer used by a saved puzzle.

**Impact:** Unused personal photographs can remain indefinitely until a later import happens to prune them or the app is deleted. Provider cache and own-photo files may also participate in device backup depending on actual resource values and platform behavior, widening retention beyond the plain-language promise even though files are not sent to the developer.

**Fix:** Put permitted disposable provider data in Caches. Give own-photo files explicit reference ownership and prune only after a successful session commit/clear/completion transition makes them unreferenced. Decide whether own-photo puzzle assets should be backed up; either apply the appropriate exclusion or update privacy/support copy to describe backup/restore accurately.

**Acceptance criteria:** Filesystem test verifies directory and backup attribute by asset type; old own photos are removed after successful replacement/clear according to the contract but survive failed/cancelled starts; no referenced photo is deleted; privacy copy matches actual behavior; reinstall/restore and low-storage eviction paths are tested.

### BUILD-01 — Documented clean install is not reproducible

**Evidence:** Reproduced. `npm ci` failed on a clean audited worktree because `package-lock.json` lacked ten optional `lightningcss` platform entries expected by the current npm resolver. `README.md` and `RELEASE.md` prescribe `npm ci`; the project does not pin Node/npm via `engines` or `packageManager`.

**Impact:** Release and CI outcomes depend on local tool versions or an already-populated dependency tree.

**Fix:** Choose and pin the supported Node/npm pair, regenerate/repair the lockfile under that toolchain, and verify on a clean machine/container. Do not paper over the failure with a non-locking install in release automation.

**Acceptance criteria:** Fresh clone with the documented version runs `npm ci` and the full check without modifying tracked files.

### META-01 — Release documentation, screenshots, and review notes do not match the candidate

**Evidence:** Code/document confirmed. `RELEASE.md` still says the Worker is not deployed and the archive is not uploaded, while also claiming support URLs are public. Screenshot guidance marks the current set partial and “Do not upload,” and the images predate major Home/setup/tray/zoom changes. Review notes describe a different premium entry and a smaller difficulty set. `BACKLOG.md` also contains stale cut-type assumptions.

**Impact:** Operators can follow false instructions; reviewers see behavior that disagrees with the notes; stale screenshots weaken trust and may be rejected.

**Fix:** Replace mutable prose with a dated release checklist generated from explicit evidence. Refresh notes and screenshots only after the exact build 3+ candidate is frozen.

**Acceptance criteria:** One owner signs each gate with date, artifact/build number, and evidence link. App Store notes and every screenshot match the installed TestFlight candidate.

### QA-01 — The exact signed candidate has no physical-device/TestFlight proof

**Evidence:** Scope-confirmed. Source checks and simulator builds pass, but build 2’s source configuration is invalid and a source-equivalent Release build fails launch. There is no current physical-device or TestFlight evidence for purchase, restore, memory, accessibility, photo picker, offline resume, or iPad layout.

**Impact:** Simulator success cannot establish App Store readiness, StoreKit behavior, gesture ergonomics, thermal/memory behavior, or device-only accessibility.

**Fix:** Run the release matrix in section 9 against the exact build 3+ archive/TestFlight binary after all other P1 gates pass.

**Acceptance criteria:** Signed QA record references the immutable build number and devices/OS versions; failures generate linked issues rather than being waived verbally.

### SEC-01 — Legacy local Unsplash credentials remain present and revocation is unproven

**Evidence:** Local/config-confirmed. The gitignored root `.env` still contains both legacy Unsplash access- and secret-key entries. Neither value was printed or copied into this report; neither value appeared in the audited archive bundle. `RELEASE.md` already instructs operators to treat them as compromised, revoke them, and remove the local entries, but no current revocation receipt exists (`RELEASE.md:20`, `:74`, `:96`).

**Impact:** A forgotten credential may remain usable outside the intended Worker boundary, and local release tooling can accidentally inherit stale configuration unless every path reliably disables dotenv loading.

**Fix:** Revoke both legacy values in Unsplash, prove the old access key no longer works, remove the root entries, and keep the replacement only in the reviewed Cloudflare secret store or a scoped gitignored Worker-development file. Keep the release archive path fail-closed with `EXPO_NO_DOTENV=1`.

**Acceptance criteria:** Dated revocation receipt; negative probe for the old access key; root `.env` no longer contains either legacy variable; secret scan of tracked files and exact archive passes.

## 6. P2 — launch quality and reliability

### PLAY-01 — Replay retains tray state; camera state follows the same reset lifecycle

**Evidence:** Reproduced for tray position; code-confirmed risk for shared camera values. After completing a puzzle and choosing **Play again**, the new tray started near the previous scroll end with the first piece partly clipped. `trayScroll` resets only when the engine identity changes, while replay resets the existing engine (`PuzzleBoard.tsx:415`, `:502`; `GameScreen.tsx:232`). Camera translation/scale share the same lifecycle, so a zoomed solve can also leave the completion reward and replay cropped; native pinch reproduction remains part of device QA.

**Fix:** Add an explicit round/session generation key and reset tray, camera, focused piece, guides, image-error state, and entrance state whenever replay starts.

**Acceptance criteria:** Replay always begins at tray origin and default fit; a test mutates every board-local state before replay and asserts full reset.

### PLAY-02 — Opening the puzzle menu does not pause the timer

**Evidence:** Reproduced. HUD advanced from approximately `0:01` to `0:08` while the menu was open for roughly 4.5 seconds. Timer lifecycle does not include menu visibility (`GameScreen.tsx:141`, `:387`; `usePuzzleSession.ts:274`).

**Fix:** Define solve-time semantics explicitly. Recommended: pause for full-screen menu, app background, system picker/dialog, and blocking alerts; keep running for lightweight settings only if intentionally stated.

**Acceptance criteria:** Fake-clock lifecycle tests cover menu, background/foreground, interruption, completion, replay, and resume without double-counting.

### PLAY-03 — Next Puzzle forgets source/category intent

**Evidence:** Code-confirmed. `GameScreen` calls `fetchPuzzlePhoto(undefined)` for Next and does not persist the chosen category. After own-photo play, Next unexpectedly switches to remote random content (`GameScreen.tsx:239`).

**Fix:** Persist source and category as session intent. Offer explicit actions: **Another from Nature**, **Choose another photo**, and, for own photos, **Use another of my photos**. Never silently cross from local to provider content.

### PLAY-04 — Completion is intentionally ephemeral, leaving no durable result

**Evidence:** Code-confirmed product/data contract, not an accidental engine failure. Completion clears the persisted session, and the completion screen is only in-memory (`usePuzzleSession.ts:329`, `:390`; `GameScreen.tsx:219`). A cold launch therefore loses the completed image/time and any path to compare or revisit it.

**Fix:** Persist a compact completion receipt before clearing active progress: photo ownership/reference, cut, size, duration, date, and optional best-time relation. Apply provider retention rules to any image reference.

### PLAY-05 — Initial tray surface extent is dropped during session creation

**Evidence:** Code-confirmed. Screens pass `traySurfaceExtent`, but start/replacement destructuring omits it. Game later detects a mismatch and regenerates the cut (`usePuzzleSession.ts:33`, `:542`, `:639`; `DifficultyScreen.tsx:389`; `GameScreen.tsx:183`, `:856`).

**Impact:** Duplicate work, an initially incorrect save, and potential visual jump or descriptor mismatch.

**Fix:** Carry the measured extent through the candidate/session contract and make cut generation single-owner. Assert the saved descriptor equals the first rendered descriptor.

### PLAY-06 — Image load failure becomes sticky

**Evidence:** Code-confirmed. Board switches from local to remote once; subsequent failure displays a terminal state with no retry/reset tied to connectivity (`PuzzleBoard.tsx:392`, `:497`, `:950`).

**Fix:** Add bounded retry with explicit user action, connectivity-aware messaging, and a route back that preserves the old session. Clear image failure on URI/session/replay change.

### DATA-02 — Corrupt saves are silently deleted and presented as no session

**Evidence:** Code-confirmed. Persistence removes invalid data and resolves to an empty state without surfacing recovery context (`PuzzleSessionPersistence.ts:692`).

**Impact:** A user sees unexplained progress loss, and the team receives no diagnostic signal.

**Fix:** Quarantine a redacted corrupt envelope for support/telemetry, show a calm recovery message, and record schema/error code. Never upload photo contents.

### PERF-01 — Large own photos are limited by file bytes, not decoded pixels

**Evidence:** Code-confirmed risk. Selection validates aspect ratio and a 20 MB compressed file limit but does not cap pixel dimensions or downsample before copying (`ownPhotoSelection.ts:22`; `ownPhotoLibrary.ts:41`).

**Impact:** A compressed 48 MP image can create large decode/texture allocations and trigger memory pressure or termination.

**Fix:** Read dimensions, enforce a pixel budget, downsample/orient into a puzzle-sized local derivative, and preserve no more metadata than needed.

**Acceptance criteria:** Physical-device tests with 48 MP HEIF/JPEG, panorama, portrait orientation, iCloud-backed selection, and low-memory interruption.

### PERF-02 — Runtime cutter fallback can perform heavy synchronous work on-device

**Evidence:** Code-confirmed risk. Missing/malformed baked assets fall back to phase-field generation with no `AbortSignal`; the solver performs synchronous heavy loops (`bakedCutSource.ts:9`, `:42`; `createPhaseFieldCutter.ts:99`; `src/puzzle/types/cutter.ts:91`).

**Impact:** A packaging regression can become a multi-minute UI stall rather than a loud release failure.

**Fix:** Production builds should fail closed when required baked cuts are absent or invalid. If runtime generation remains a development tool, isolate it from shipping code and make it cancellable/off-main-thread.

### PERF-03 — 196-piece mode lacks a physical performance budget

**Evidence:** Code-confirmed risk. The board creates up to 196 animated/gesture subtrees and guide paths. Entrance delay grows by 34 ms per index, so the final piece begins roughly 6.6 seconds after the first; delayed pieces may already participate in input/accessibility (`PuzzleBoard.tsx:457`, `:709`).

**Fix:** Cap total entrance duration around 400–700 ms, disable hit/accessibility until visible, and profile frame time, memory, gesture latency, and snapping on supported low-end hardware. Review the screen-space effect of logical hit/snap thresholds under 3× zoom.

### A11Y-01 — Reduced Motion does not cover piece gesture springs

**Evidence:** Code-confirmed. Board, menus, and celebration respect reduced motion in several paths, but `usePieceGesture` always uses spring animations (`usePieceGesture.ts:107`). Unconditional haptics are tracked separately as the A11Y-03 preference follow-up.

**Fix:** Centralize motion preferences. Under Reduce Motion, replace spatial springs/entrances with immediate or low-motion transitions.

### A11Y-02 — Setup cut cards truncate and crowd locks on a standard iPhone

**Evidence:** Reproduced on iPhone 17 Pro simulator. Labels such as Crystal and Amoeba were visibly truncated, and lock badges competed with label space.

**Fix:** Use a layout that can fit eight options at accessibility text sizes: two-line labels, a wider card/list, or separate lock placement. Do not rely on ellipsis to distinguish purchasable styles.

### UX-01 — There is no first-run gesture teaching

**Evidence:** Code/product confirmed. Store metadata mentions pinch interaction, but the app offers no visible tutorial for drag, tray scroll, pinch zoom, two-finger pan, or Assist discovery.

**Fix:** Add contextual, dismissible teaching on the first relevant action, plus a replayable Help entry. Teach one gesture at a time and avoid blocking the board.

### UX-02 — The visual HUD intentionally omits progress and time

**Evidence:** Code-confirmed product choice. Progress/time are present in accessibility output but not rendered visually in the regular HUD (`GameHud.tsx:22`). This is not an accessibility failure; it is a feedback/engagement tradeoff.

**Fix:** Add an unobtrusive `placed / total` and elapsed-time presentation, with a setting to hide time for calm play.

### UX-03 — The player cannot change size/cut or re-cut the same photo in-game

**Evidence:** Product confirmed. Menu offers table, guide, music, assist, return, and leave, but no reconfigure action.

**Fix:** Add **Restart / Re-cut this photo** with explicit progress-loss confirmation. Preserve photo source and attribution. This also makes premium discovery less dependent on abandoning the current loop.

### UX-04 — Premium messaging and post-purchase flow are inconsistent

**Evidence:** Code-confirmed. Paywall copy names only Organic and Living even though seven premium cuts are offered. Home maps several saved premium cut names to “Organic.” After successful purchase the sheet closes, but Start must be tapped again (`PremiumCutsSheet.tsx:161`; `DifficultyScreen.tsx:90`, `:787`; `PlayHomeScreen.tsx:86`).

**Fix:** Generate names/features from the cut catalog, return the purchase result to the pending Start intent, and continue automatically after entitlement confirmation. Give restore and purchase errors specific recovery copy.

### UX-05 — Switching cuts can silently change piece count

**Evidence:** Code-confirmed. Setup selects the nearest supported size when the chosen cut does not support the current size (`DifficultyScreen.tsx:340`).

**Fix:** Explain the change inline before applying it, or disable incompatible cuts with the supported range. Preserve the user’s last size per cut if useful.

### OBS-01 — Client and Worker observability are insufficient for launch

**Evidence:** Code-confirmed. The app error boundary announces failure but does not report it and cannot catch all async/native failures. Worker diagnostics are primarily console warnings; health checks validate bindings/key presence rather than upstream service behavior (`server/src/index.ts:1221`).

**Fix:** Add privacy-safe crash/error reporting and operational metrics without photo URLs/contents or sensitive identifiers. Add synthetic/canary health for upstream fetch and Durable Object behavior, sampling and redaction, dashboards, alerts, and a kill switch.

### TEST-01 — Unit coverage is broad but lifecycle/UI coverage is missing

**Evidence:** Code-confirmed. The suite has strong pure engine/persistence/contract tests but no component/navigation/device E2E layer or CI workflow. Current tests did not detect retry source-switching, menu timer, replay state, preparation cancellation, or transaction ordering.

**Fix:** Add focused component/integration tests first, then a small deterministic device smoke suite. Avoid trying to automate every visual detail.

**First integration targets:**

1. Candidate-session transaction with injected failures at every await boundary.
2. Start → Back/unmount/background cancellation.
3. Own-photo validation and source-specific retry.
4. Replay reset of every board-local state.
5. Menu/background timer semantics.
6. Next preserves category/source intent.
7. Public-link and archive-configuration release guards.

### DEP-01 — Dependency advisories need owner triage

**Evidence:** Reproduced. Root production audit reports 27 moderate/high advisories, largely via Expo/Metro tooling; server production dependencies report zero.

**Fix:** Classify each advisory as shipped runtime, build-only, unreachable, or actionable; upgrade on a dedicated branch with build/test evidence. Do not claim zero vulnerability merely because many are build-chain packages.

### REL-03 — Archive symbol upload warnings need a deliberate crash-symbolication decision

**Evidence:** Artifact/log-confirmed. Organizer packaging reported symbol-upload failures for React, ReactNativeDependencies, and Hermes; the archive contains the app dSYM but not those dependency dSYMs.

**Impact:** Framework/native crashes may be harder to symbolicate. This is not a proven launch crash or automatic rejection, but it weakens incident response at the same time the app has no crash SDK.

**Fix:** Determine which dependency dSYMs are expected for this Expo/React Native build path, make symbol upload deterministic where possible, and document how an App Store/Organizer crash is symbolicated end-to-end.

**Acceptance criteria:** A controlled native crash from a release-like build produces a useful symbolicated report, or an explicit reviewed limitation and alternative diagnostic path is recorded.

## 8. Architecture assessment

### Strengths to preserve

- Engine, cut descriptors, rendering, persistence, and screens have useful seams rather than one monolith.
- Cut generation is deterministic and has substantial pure test coverage.
- Premium access is designed to fail closed against an exact product contract.
- Persistence uses a serialized queue and image-cache ownership concepts, which are a solid base for transactional repair.
- Gallery and next-puzzle request races already have defensive patterns; extend them to preparation/session commit.
- Worker request schemas, allowlists, body limits, single-use grants, and durable tracking queue are thoughtful foundations.
- The privacy footprint is small: system photo picker, no camera/microphone permission, and no obvious advertising tracker.
- Accessibility foundations are materially better than average: 44-point controls, descriptive piece labels, custom Assist actions, announcements, Dynamic Type use, and reduced-motion handling on several major surfaces.
- Free play spans 9–196 pieces and guide modes are independent from cut purchase.

### Recommended target boundary

Use a two-phase candidate/commit model for both initial and next puzzle:

```text
User intent
   ↓
Prepare candidate (photo, entitlement, cut, files)
   ↓
Durably enqueue required provider event
   ↓
Atomic session commit + image ownership transfer
   ↓
Render/navigate
   ↓
Retire prior session files
```

Every phase must accept cancellation and be idempotent. The active session pointer should never reference a half-prepared candidate, and candidate cleanup should never delete the prior active image.

For 1.0, choose one persistence product:

- **Single active puzzle:** smallest change; add explicit replacement confirmation, transactional rollback, and completion receipt.
- **Four-slot shelf:** stronger retention; connect the existing pure shelf logic to UI and image lifecycle. Do not partially enable it without ownership/eviction tests.

## 11. Deliberate deferrals for a narrow 1.0

Do not make these release blockers unless the product promise changes:

- clusters and rotation;
- Android;
- localization beyond English;
- more cut styles;
- multiplayer/social systems;
- sophisticated audio mixing;
- broad gallery search/favorites;
- a full analytics warehouse.

The release should still include privacy-safe crash visibility and a minimal funnel (`home → photo selected → setup → started → completed → next/replay/exit`) because operating blind during launch is not a safe deferral.

## 12. Definition of “ready to submit”

Frume is ready to submit only when all of the following are simultaneously true for the same immutable build:

1. Clean install and full checks pass from a pinned toolchain.
2. Archive guard proves production RevenueCat configuration and expected endpoints.
3. Clean physical launch, purchase, restore, and core loop pass in TestFlight.
4. Support and privacy pages are anonymously public.
5. Unsplash delivery, storage, attribution, and use tracking follow a documented contract.
6. Worker global budget, monitoring, alerting, and kill switch are live.
7. Replacement/cancellation/force-quit tests prove no silent progress or tracking loss.
8. Required accessibility and performance device matrix passes.
9. Screenshots, notes, privacy answers, and product copy match the exact binary.
10. The signed transaction proves canonical GitHub source parity and binds the
    exact Cloudflare-generated Worker version through its live ten-check health
    response.
11. Workers Paid capacity, migrations, rotated secrets, legacy-key revocation,
    provider allowance, monitoring, alerting, and kill-switch exercises are
    recorded for the active deployment.
12. Crash visibility and symbolication have an explicit, tested operating
    contract.
13. DSA, privacy, age rating, export compliance, platform availability,
    agreements, banking/tax readiness, screenshots, and reviewer metadata are
    complete in App Store Connect.
14. The release checklist names the artifact, build number, evidence, owner,
    and date for every gate in `RELEASE.md`.
